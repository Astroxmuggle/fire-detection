Motivation & Context

Problem Statement: Why Vision-Based Fire Detection?

⚠️ Traditional Point Sensor Limits
  • Convective Delay: Particles must physically drift to ceiling detectors, taking minutes.
  • High-Ceiling Ineffectiveness: Fails in open warehouses, airports, and stadiums.
  • Zero Outdoor Utility: Cannot monitor perimeters, forests, or yards.
👁️ Computer Vision Advantage
  • Instant Line of Sight: Detects visual flames within fractions of a second (<200ms).
  • Dual Flame & Smoke: Detects rising smoke plumes before flame breakout.
  • Reuses Infrastructure: Integrates with existing CCTV setups.
🛡️ Core Technical Challenges
  • False Alarm Fatigue: Glare, red shirts, and headlights trigger naive detectors.
  • Compute Restraints: Heavy models require $2,000+ GPUs. We target 20+ FPS on CPU.
In warehouses and high-ceiling facilities, traditional smoke detectors suffer from severe lag because combustion particles must drift upward. CCTV-based vision solves this with zero transit delay. However, false alarms from headlights or glare and heavy GPU requirements remain the primary challenges we set out to solve.
Architecture

End-to-End System Architecture

1. Capture & Inference
  • OpenCV video ingest from webcam or RTSP stream.
  • YOLO11 Nano running at 640x640 resolution.
  • Class filtering and Non-Maximum Suppression (NMS).
2. Temporal Confirmation
  • ConfirmationTracker state machine.
  • Enforces 2+ consecutive-frame detection consensus.
  • Instantly resets and discards single-frame transient noise.
3. Forensics & Delivery
  • Automatic evidence snapshot capture with bounding boxes.
  • SQLite transactional logging (`detection_events`).
  • Flask MJPEG live stream & REST API dashboard.

Deep Learning

Model Selection: YOLO11 Nano Architecture & Dataset

Why Ultralytics YOLO11n?
  • 2.6M Parameters: Compact 5.6 MB model size.
  • Realistic on CPU: ~4.7 FPS at 640×480 on an 8-core laptop CPU, with no GPU.
  • Decoupled Detection Heads: Separates classification from regression for tighter bounding box fit.
  • Dual Classes: Jointly optimized for 'fire' and 'smoke'.
Training Dataset & Hyperparameters
  • Benchmark: Roboflow Fire & Smoke Dataset (CC BY 4.0).
  • Diversity: Multi-scene distribution (forests, indoors, factories, night).
  • Augmentations: 4-image Mosaic, affine transforms, HSV jitter.
  • Training Regimen: 50 Epochs, batch size 16, SGD/AdamW cosine scheduler.
We chose YOLO11 Nano for its lightweight 2.6 million parameter footprint. It runs smoothly on CPU while maintaining strong feature extraction for amorphous smoke and vibrant flames.

Algorithmic Innovation

Temporal Confirmation Tracker

The Problem: Single-Frame Flickers
  • Standard detectors evaluate each frame in total isolation.
  • Light reflections, lighters, or vehicle lights can produce 0.51 confidence for just a single 30ms frame.
  • In naive systems, this causes constant false alarms.
Consensus State Machine
  • Candidate State: First detection increments candidate counter.
  • Temporal Threshold: Must persist for $N \ge 2$ consecutive frames before confirmed status.
  • Fast Reset & Latch: One event per incident; the class re-arms after 3 clear frames.
  • Low Latency: 2 frames add ~0.4 s at ~5 FPS — still far below human response time.
Our temporal tracker prevents single-frame false alarms, tracks fire and smoke independently, and latches after confirmation so one incident produces one event. At roughly five frames per second it adds about 0.4 seconds of latency.

Hard-Negative Evaluation (FIRESENSE Dataset)

Smoke-Negative Clip (45.1s)
  • Challenging outdoor video with moving clouds and tree shadows.
  • 0 Raw Detections on this clip.
  • 0 False Confirmations (100% specificity on this clip).
Fire-Negative Clip (15.5s) & Analysis
  • Night scene with headlights reflecting off wet road asphalt.
  • 7 raw detections → one confirmed false alarm (four before the latch fix) due to sustained specular glare.
  • Academic Insight: Proves that temporal tracking must be coupled with chromatic (Cr/Cb) and flame flicker (10–13 Hz) analysis in future production versions.
Testing against the FIRESENSE benchmark showed 100% specificity on daytime outdoor smoke-negative footage. On wet-road headlight reflections, the glare persisted, revealing that future versions should combine temporal tracking with flame flicker analysis.
Forensics & Persistence

Evidence Capture & Alert Architecture

1. Evidence Snapshots
  • Automatically saves full-resolution annotated frames.
  • Timestamped cryptographic filenames stored in `/snapshots`.
2. SQLite Persistence
  • `detection_events` table stores class, confidence, and snapshot URI.
  • `alerts` table records acknowledgment workflow.
3. Alert Manager
  • Local audio buzzer with system frequency fallback.
  • 60-second cooldown suppresses alert spam during ongoing fires.
Confirmed incidents save an uncompressed evidence snapshot, log a record to SQLite, and trigger an alert with a 60-second cooldown to prevent alarm spamming.

Interface

Operator Dashboard & RESTful Management API

Flask Web Dashboard
  • Live MJPEG video stream rendered directly at `/video_feed`.
  • Honest status badges driven by real runtime state (camera, model, stream).
  • Incident history table linking to a detail page with the stored evidence frame.
  • One-click operator acknowledgement from the incident page.
REST API Endpoints
  • `GET /api/status` — Real camera/model state and event counts.
  • `GET /api/events` — Filtered historical incident queries.
  • `POST /api/alerts//acknowledge` — Silence an active alarm.
  • `PUT /api/settings` — Update thresholds for new capture sessions, no restart needed.
The operator dashboard provides real-time situational awareness with live video streaming, evidence inspection on the incident page, and RESTful control for external building management systems.
Roadmap

Limitations & Future Work

Current Boundaries
  • Intended as an auxiliary monitor, not a replacement for certified NFPA alarms.
  • CPU-bound: ~4.7 FPS at 640×480 on an 8-core CPU; a GPU or ONNX/OpenVINO export is the obvious next step.
  • Single camera per process (RTSP URLs are supported, a camera registry is not).
Future Enhancements
  • Remote Alerting: SMTP email with attached snapshots, Telegram bot, and SMS.
  • Multi-Camera RTSP: Simultaneous multi-zone surveillance.
  • Flame Flicker FFT: 10–13 Hz frequency filtering to eliminate headlight glare.
We are clear about our prototype limitations. Future enhancements will add remote SMTP/Telegram alerts, multi-camera support, and flame flicker frequency filtering.
